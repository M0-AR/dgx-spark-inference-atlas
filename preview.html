What this is, in plain words

The idea

Smaller models, same job?

A big AI model can be squeezed from 16 bits per weight down to 4, 3, even 2 — making it smaller, faster and cheaper to run. The question everyone assumes is answered: does it still work? Especially when the model must call tools — fetch a live bitcoin price, convert currencies, format strict JSON — rather than just chat.

The approach

Measure like it's a clinical trial

Every rule — what counts as success, how many runs, which statistical test, what passes as “equivalent” — was written down before any measurement. That's called pre-registration, and it's the strongest defence against accidentally (or conveniently) fooling yourself.

The evidence

Numbers no one can type by hand

Each published table is regenerated mechanically from committed run files. If it's in a table, it came from an artifact — and re-running the generator produces byte-identical output. Sounds strict? That's the point.

How the machine works — 4 steps

This is the full lifecycle of one measurement, from a model answering a question to a number safe enough to print.

STEP 1 · SERVE

Ask a real question

An episode hands the model a task: “Get the BTC price in EUR and answer in strict JSON.” The model must decide which tools to call, call them correctly, and format the answer.

runner.py serves each condition in isolation with a drained warm-up, so one condition never disturbs the next.

STEP 2 · FETCH

Live truth, captured

At episode time the harness fetches real prices — Kraken for BTC/USD, ECB reference rates for EUR/USD — and records the URL, the response, and its SHA-256 fingerprint.

live_data.py · the served values become the episode's truth; no memorized answers can pass.

STEP 3 · GRADE

Three honest checks

C_tool: were the tool calls valid? C_task: was the final JSON correct, within pre-set tolerances, and internally consistent? C_outcome: both, with no repair needed.

toolcall_eval.py · a repaired success is a success for C_task but never for C_outcome.

STEP 4 · PUBLISH

Numbers, mechanically

Tables, statistics and the README's figures are generated from the committed records by a single script — and re-running it reproduces identical bytes.

sync_readme.py · no README number is hand-typed, ever.

Why this matters

You can't fake it by memorizing

A model that “remembers” last year's bitcoin price fails instantly — the tolerance check compares against today's value, fetched live. This is what makes the test a true agentic test: it forces the model to actually call its tools.

Audit trail

Two snapshots, three seconds apart

The harness captured two independent snapshots before big runs. Both agree on the FX leg (identical SHA-256) and on the BTC leg — a self-check the project runs before accepting any results. Files: snapshot 1 · snapshot 2.

Verification — what you can trust, and why

Claims are separated into what is proven today, what is in progress, and what is deliberately left external.

  • ✅
    Statistics validated against known values16 tests pin exact numbers for McNemar's test, bootstrap determinism, chi-square values, changepoints, equivalence testing and more — so the harness never judges a model with an untested judge.
  • ✅
    End-to-end pipeline proven offline2 mock-server tests run a real streaming server through the full runner, plus a Docker Compose “reproducibility floor” that executes the suite in a container — no GPU required.
  • ✅
    Live-data graders proven end-to-endA mock episode is graded against genuinely live Kraken/Frankfurter data; the grader test skips cleanly when offline rather than ever “passing” without network.
  • ✅
    Everything mechanicalREADME tables, LaTeX macros and the provenance manifest are regenerated by one script from results/. Re-runs are byte-identical; a hash change without new raw artifacts is treated as tampering.
  • ✅
    Mock runs excluded by rulePipeline smoke runs (model “mock”) are committed for inspection but can never appear in a results table.
  • ✅
    Deviations recorded, not papered overThe local arm runs on an RTX 3090, not a GB10 — stated openly, with transfer claims kept at method level until the Spark kit is run by real Spark owners.
  • ⏳
    Ladder measurements — in progressNo quantized results exist yet. The tables currently say so, literally. Fabricating placeholder numbers would violate the study's own rules, so you will see “no data yet” rows until real artifacts land.
  • 📦
    External claims stay externalCommunity numbers about competing serving stacks are catalogued with sources and dates — including a direct contradiction — and none of them are merged into measured tables. The Spark Kit exists so anyone can adjudicate with data.

Reproduce everything

Five commands. The first two work on any machine — no GPU, no model downloads. The rest use any OpenAI-compatible endpoint you have.

# 1) harness self-tests — 19 tests (1 skips cleanly offline)
python3 -m pytest harness/tests -q

# 2) container reproducibility floor — works without a GPU
docker compose -f docker/docker-compose.yml run --rm smoke

# 3) capture environment + live market snapshot artifacts
python3 scripts/collect_env.py && python3 scripts/snapshot_market.py

# 4) serve any OpenAI-compatible endpoint, then measure
python3 -m harness.bench.runner --endpoint http://127.0.0.1:8080/v1 \
    --model MODEL --tag e30 --requests 8 --reps 5 --concurrency 1,4
python3 scripts/run_toolcall.py --endpoint http://127.0.0.1:8080/v1 \
    --model MODEL --tag e30 --episodes 30

# 5) regenerate every number in the README from the artifacts
python3 scripts/sync_readme.py

GPU toolchain (torch + ExLlamaV3): bash scripts/setup_gpu.sh · DGX Spark protocol: docs/SPARK_KIT.md
